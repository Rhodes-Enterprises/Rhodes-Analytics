# Goal data gotchas (marketing dashboards)

- DM_GOALS is **daily-distributed**: sum GOAL over the date range for a span goal and over range-start→today for a to-date goal. Do not prorate.
- Every `goal_*_qN` / `waterfall_*_<mon>` recalc GOAL_TYPE carries BUDGET_DATE rows across the whole fiscal year (Jan 1–Dec 31), not just its own quarter/month — window sums over any sub-range are valid (a January window of a q3 type is non-empty, a q1 type still has December rows).
- The four dashboard targets are encoded in GOAL_TYPE naming conventions, and "Goal"/"Waterfall" are periodically re-issued (q1/q2/q3, monthly) — resolve the goal type at runtime by walking back to the latest existing period instead of hardcoding names. `old_*` and `RL_*` (rentals) variants must be excluded for EHI dashboards.
- **Why:** hardcoded goal types silently go stale when dbt adds the next quarter/month recalc.
- Division attribution for contacts/deals only works via the community-of-interest → DM_COMPANY_DEVELOPMENT.DEVELOPMENT_NAME join (~95% match; the rest, e.g. "General", stay unattributed) — expect division tables to sum below the grand totals, same as Qlik.
- The community-of-interest → DM_COMPANY_DEVELOPMENT join must use a deduped, Esperanza-filtered dimension (one row per DEVELOPMENT_NAME, e.g. QUALIFY ROW_NUMBER()=1): the raw table holds all brands and the same development name under many companies ("VDL Lots" ×7), so joining it raw fans out actual counts ~1.5x.
- Breakdown tables must seed their row set from actuals as well as goals/GA rows — a development with sales but no goals otherwise vanishes silently (the dashboard audit's sum-vs-headline check exists to catch exactly this).
- ONSITE_ONLINE_SOURCE_CHANNEL / DEAL_ONSITE_ONLINE_SOURCE_CHANNEL hold literal labels 'Online'/'Onsite'/'Unknown' (no NULLs in practice; 'Unknown' ≈28% of deals, ~1% of contacts) — online+onsite legitimately sums below totals, and anything hardcoding those labels goes silently all-zero if dbt renames them (guard against the all-zero signature, exempting low-volume windows).
- GA data covers two brands; filter PROPERTY='Esperanza Homes' or Rhodes Living rental traffic inflates every web metric.
- GA website users are COUNT(DISTINCT USER_PSEUDO_ID) and **not additive** across companies/developments (same visitor hits several) — breakdown rows legitimately sum above the headline. Cross-check GA numbers per-row against a baseline grouped by MATCHED_COMPANY_NAME/MATCHED_DEVELOPMENT_NAME, never by summing rows to the headline.
- Goals are issued per fiscal (calendar) year, so date ranges crossing a year boundary mix goal regimes — either aggregate per year or reject such ranges explicitly.
- The EHI convention-named regime (goal_*_qN, waterfall_*_mon, business_plan_*/proforma_*_year) **starts FY2026**. FY2025 and earlier carry only legacy display names ('Gross Sales', 'Waterfall Sales', 'Onsite Leads'…) that no dashboard target resolves — past-year views legitimately show ZERO targets. **Why:** audits/features assuming past years have resolvable targets would be permanently red (or invent unvalidated legacy-name mappings); pin exact-zero fiscal isolation for pre-regime years and let real value pinning activate when FY2026 becomes a past year.
- The walk-back's old_* exclusion is value-detectable: FY2026 has old_goal_*_q3 re-issues whose sums differ from goal_*_q3 (gross sales 1200 vs 972). To regression-pin the walk-back with live data, use an elapsed-quarter range — a cutoff inside a past quarter must resolve THAT quarter's re-issue, not the newest or old_* one.
- Rhodes Living (rentals) is its own business line: actuals come from DM_DEALS PIPELINE_NAME='Rhodes Living Pipeline' with LEASE_RATIFIED_DATE / CANCELLATION_DATE; goals are RL_Leases_Ratified (+ RL_Online_/RL_Onsite_ splits) from FY2026, only RL_Leases in FY2025 — resolve with fallback. No cancellation goal exists; net leases compare against the ratified goal.
- RL upstream funnel actuals: web traffic = GA session starts (IS_SESSION_START='Yes', PROPERTY='Rhodes Living', community via MATCHED_DEVELOPMENT_NAME); leads = DM_CONTACTS with a non-empty RL_COMMUNITY_OF_INTEREST by CONTACT_CREATE_DATE; first tours = RL_MIN_FIRST_TOUR_DATE; move-ins = RL_MIN_MOVE_IN_DATE (timestamp — cast to date). Channel = ONSITE_ONLINE_SOURCE_CHANNEL. RL_Web_Traffic and RL_Move_Ins goals have no online/onsite splits (leads/tours do), and FY2025 only had RL_Leads/RL_Tours.
- RL community lives in RL_COMMUNITY_OF_INTEREST_HUBSPOT_DEAL and contains trailing-space variants ("Belterra ") — always TRIM before grouping/filtering, or communities split into duplicates.
- DM_MARKETING_DASHBOARD_INPUT_GOAL_RATIOS is keyed (MARKETING_GOAL_YEAR, MARKETING_GOAL_NAME_RATIOS) and the names match the dashboard's ratio labels verbatim (all 10 present for 2022–2026; some 2022 values are 0, which the dashboard treats as "no PTG"). The table contains junk rows (NULL year / NULL value) — always filter by year AND skip NULL values. Audits should resolve names in BOTH directions (every dashboard ratio must resolve; no orphaned table rows) so a dbt rename can't silently null a goal.
- When auditing a derived ratio against independently re-queried counts, use the compounded drift bound (1+t)/(1−t)−1 where t is the per-count tolerance (each count may legitimately drift between the API's ~5-min cached read and fresh baselines). Genuine wiring bugs (swapped numerator/denominator, wrong actual) diverge by orders of magnitude beyond it, so the wider bound loses no detection power.
- Every RL_* goal type carries per-community DEVELOPMENT_NAME rows (including all-zero rows), so per-community funnel goals come straight from DM_GOALS. But contact community names don't fully align with goal names ("Villas Las Lagunas" actuals vs "Villas Las Lagunas - Rentals" goals; "General_Rental" pseudo-community has no goals) — show each source's name as its own row rather than aliasing, and expect some rows with actuals-only or goals-only.
- GA per-community traffic (MATCHED_DEVELOPMENT_NAME, PROPERTY='Rhodes Living') maps only some communities; unmatched sessions have NULL development but still count in the site-wide total. Per-community traffic must render null (dash) for unmapped communities — never 0 — and mapped rows won't sum to the headline.
