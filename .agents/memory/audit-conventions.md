---
name: Audit tolerance conventions
description: How dashboard audits set divergence tolerances against cached endpoints, how their timeout layers must nest, and how membership spot-checks dodge cache staleness
---

- When an audit compares a same-day-cached endpoint (day-stamped cache keys) against fresh Snowflake baselines, do NOT use exact equality or a flat absolute tolerance. Bound each value by the cache-consistent window: `baseline − todayStampedCount − slack ≤ api ≤ baseline + slack`, where todayStampedCount is fetched per row alongside the baseline (one `COUNT_IF(dateCol = today)` in the same GROUP BY) and slack = max(2, TOLERANCE_PCT% of baseline) absorbs rare restatements of past days. The "today" in that COUNT_IF must be the SAME day convention the endpoint uses — America/Chicago everywhere in this project, never UTC (a UTC "today" flips at 6-7pm Chicago and once made the Community List reset YTD hours early on New Year's Eve; endpoint and audit must roll over together).
  **Why:** the cache legitimately lags today's activity by up to a day; exact checks flake on busy afternoons, while flat floors are either flaky in January (small YTD, hot day) or too loose to catch small real regressions. The window stays tight when a row had no activity today (the common case) and is independent of cache TTL details — which other tasks keep changing.
  **How to apply:** reuse when adding per-row numeric audits for any other cached dashboard endpoint (leasing, funnel, etc.). Real join regressions (zeroed, duplicated, cross-wired counts) blow far past the window. Reference implementation: the Community List YTD section of the dashboard audit script.
- Verify new audit checks can actually FAIL: run the audit once through a tiny local proxy that forwards to the real server but doctors the one response under test (inflate one value, zero another), and confirm exactly the expected FAIL lines + exit 1. Cheap, needs no code changes to the audit or server. For pure Snowflake-side guards with an env-tunable threshold, tightening the threshold below the current real value is an equally cheap failure proof.
- Timeout layering: the audits' per-request deadline must satisfy (max transient retries + 1) × deadline + backoffs < the umbrella runner's per-audit budget, so a hung endpoint fails with the retry-exhausted error that NAMES the URL instead of the runner's blunt kill.
  **Why:** the runner-level kill can't say which request hung; the retry chain can. And the API server keeps computing/caching after a client abort, so a timed-out cold request usually succeeds on retry — the request deadline is a stall detector, not a latency ceiling.
  **How to apply:** re-check the inequality whenever changing the retry count, request deadline, or per-audit budget. When killing a stuck audit process, spawn it detached and signal the NEGATIVE pid: pnpm sits between the runner and the real audit process, and killing only pnpm (e.g. spawnSync's timeout) orphans the audit, which keeps hammering the shared API server. The UI audit's page-data wait is deliberately longer than the fetch deadline (cold first paint) — don't "harmonize" its API proxy fetch down to the shared deadline or cold loads will 502.
- Offline hang/stall simulations (transport-swap seams): a "hung socket" faked as a bare never-resolving Promise does NOT hold Node's event loop, and AbortSignal.timeout timers are unref'd — so the process can exit code 0 with empty output before any assertion runs (silent false green). Keep a ref'd keepalive interval for the scenario's duration and register an exit-handler tripwire that fails the run if it ends before assertions complete; treat empty harness output as failure, never success.
- Membership (dropdown-list) checks against SWR-cached endpoints: pick spot-check values using the endpoint's OWN predicates (shared modules like isLeadSql/DEV_DIM, so picks are subsets-by-construction) over a trailing window that ENDS beyond the cache's keep horizon (today−2d for keepMs=24h).
  **Why:** a busiest-value pick computed "now" can include a value whose first activity postdates a legitimately stale cached response (false positive on long-running servers); quarter-bound pick windows are empty on day one of a quarter.
  **How to apply:** reuse for any other filter-options endpoint (leasing, future dashboards): trailing ~90d window shifted back 2 days; a pick query returning nothing FAILS the audit rather than skipping the check.
- Membership checks for UNION-built dropdown lists (e.g. Leasing communities = deal ∪ goal communities): spot-check EVERY leg of the union, preferring a value ONLY that leg contributes (fallback: the leg's heaviest value when none exists).
  **Why:** a busiest-value pick that both legs contain passes even when one leg silently drops out; preferring a leg-exclusive value makes the check fail exactly when the dropout would actually shrink the shipped list — and never vacuously.
  **How to apply:** restate the OTHER leg's predicates in a CTE to define "exclusive" (ORDER BY exclusive DESC, mass DESC LIMIT 1). For legs from bulk-loaded tables with no insert timestamp (DM_GOALS), bound the pick by the table's own date column (BUDGET_DATE ≤ window end) instead of an activity window; also restate — never import — the endpoint's predicates in picks, so an accidental WHERE change diverges loudly instead of moving the picks with it.
- Freshness guards for lagging external exports (e.g. GA → Snowflake, which normally trails today by ~7-8 days): never test "rows exist today"; fail when MAX(date) trails today beyond a threshold comfortably above the normal lag (env-tunable, default ~2x). For multi-stream tables (e.g. one row-stream per analytics property), also bound EACH expected stream's own max date — the table-wide MAX stays fresh while a single stream dies. Validate numeric env thresholds with Number.isFinite: `lag > NaN` is always false, which silently disables the guard in the direction that never alarms.
- Reading audit:all's outcome from a shell pipeline: `pnpm run audit:all | tee log; echo $?` reports TEE's exit (a false 0 over a failed suite). Use `set -o pipefail` first, and cross-check the run's own `──── audit:all summary ────` block — it lists per-audit PASS/FAIL and is the ground truth.
- Parallel-task merges/rebases can silently duplicate top-level blocks in the audit scripts (same-name helper functions, memoized cache `let`s) — even inside a single sibling's already-merged commit — which breaks ESM load (`symbol has already been declared`) or, worse, leaves two coexisting contracts for one helper.
  **Why:** git resolves hunks positionally, so two branches adding/moving the same function merge "cleanly" into two copies; conflict-marker absence proves nothing about semantic coherence.
  **How to apply:** after every conflict-resolution round, run an esbuild parse (`esbuild --bundle --packages=external`) on each touched script AND scan for duplicate top-level declarations (grep `^(async )?function |^let |^const ` → sort | uniq -d); diff the result against main's tip and account for every non-mechanical line. When main itself ships the duplicate, repair it in the resolution and record it via divergenceSummary.

## Deadline-race scenarios have two legitimate exits
When a bounded query can fail via either of two named paths (e.g. queue-slot timeout vs retry-deadline, decided by whether capacity frees moments before the deadline), don't assert which path in a racy setup — assert the shared bound and the union of named errors there, and pin each specific path in its own deterministic scenario. **How:** a rogue transport that ignores its abort signal and never settles pins slots forever, making the queue-timeout path deterministic; run it last (pinned state only unwinds at process exit) and after any process-wide pause gates from earlier scenarios have drained.
