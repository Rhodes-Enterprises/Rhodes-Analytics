---
name: Dashboard query cache (stale-while-revalidate)
description: Rules for the shared SWR cache all dashboard query layers must use, and why refreshes are traffic-triggered only
---

- All dashboard data layers route Snowflake reads through the ONE shared SWR cache module — never a private per-lib TTL cache.
  **Why:** per-lib copies drift (one lib silently lost single-flight dedupe), and plain TTL caches go cold every expiry, recreating the slow-first-load problem SWR exists to fix.
  **How to apply:** new dashboard lib → reuse the shared cache factory/instance; stale entries serve instantly and refresh in the background.
- Cache refreshes stay TRAFFIC-TRIGGERED only (plus the one-shot boot warm-up) — no cron/interval warmers.
  **Why:** idle-time re-querying keeps the Snowflake warehouse from auto-suspending and burns credits all night. Accepted tradeoff: the first visit after a long idle stretch sees data as old as the idle stretch (bounded by the keep window) while a refresh runs behind it.
- Background refreshes share one small process-wide concurrency gate across ALL cache instances; don't raise it without re-checking the combined foreground+background burst against the proxy's ~10 req/s repl budget (one page view can find many stale entries at once).
- Cold-miss fan-outs need their own bound: the global refresh gate covers only SWR refreshes; an endpoint Promise.all of ~15 queries can alone breach the ~10 RPS proxy budget when contended (boot warm-up, audits). Cap per-endpoint bursts (~4-wide limiter).
- The SWR contract is enforced by an auto-discovered audit script; its timing-sensitive checks need >=250ms margins from every fresh/keep boundary or they flake at the boundary.
- Dashboard responses carry an honest freshness stamp: routes wrap their data assembly in the cache module's AsyncLocalStorage tracker, every cached() lookup reports its entry's load time, and the OLDEST one wins (`dataAsOf`), plus a `refreshing` flag when a stale serve has a refresh actually in flight.
  **Why:** SWR deliberately serves yesterday-evening numbers to the first morning visitor; without the oldest-entry stamp people quote stale numbers in meetings. Client fetch time (react-query dataUpdatedAt) is NOT the data's age — don't reuse it as such.
  **How to apply:** new dashboard endpoints → wrap the lib call in withDataFreshness and include `dataAsOf`/`refreshing` in the payload + OpenAPI schema; background revalidations must run detached from the tracker (storage.exit) or their nested lookups stamp whichever request triggered them; after a failed refresh, the stamp stays old while `refreshing` is false during the cooldown — that is correct, not a bug.
- Patient Retry-After-honoring 429 retries inside the background-refresh wave can SUSTAIN the saturation they're waiting out: ~12 stale entries × fan-out, each retrying ~1 RPS, keeps the ~10 RPS proxy pinned, and concurrent audit baselines (equally patient) can exhaust attempts and die mid-suite.
  **Why:** the proxy budget is zero-sum per repl; everyone backing off politely still sums past the cap when the wave is wide. Observed killing audit:leasing ~5min after the audit server's warm-up (entries go stale mid-suite → wave + baselines collide).
  **How to apply:** treat 429 storms lasting ~a minute in audit logs as this collision (rerun-flaky), not data breakage; any real fix must throttle at the per-query level across foreground+background, not per-entry.
- Forced refresh (`?refresh=1|true` on dashboard GETs → `withForcedRefresh` around the data call) is the sanctioned "numbers as of right now" path: it bypasses BOTH serve paths but still funnels through single-flight `load()` and stores for everyone; entries younger than `forceFreshMs` (~5s) are served as-is, which is the mash-safety cap (one upstream fan-out per window). Forced-load failures propagate to the route instead of silently serving the stale value the user asked to bypass.
  **How to apply:** every NEW dashboard endpoint should accept the shared `ForceRefresh` openapi param and wrap its data call; the web page pairs it with the shared `RefreshDataButton` (fetch with `refresh: true`, then `queryClient.setQueryData` under the normal query key so numbers swap in place with no skeleton flash and the "refreshed" badge updates). The flag rides AsyncLocalStorage at module scope, so it works across all cache instances without parameter threading.
